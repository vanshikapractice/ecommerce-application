# Admin dashboard file explanation

For the complete repository-wide learning map, workflow walkthroughs, Prisma
relationship explanation, and interview-oriented rationale, see
[codebase-learning-guide.md](./codebase-learning-guide.md).

| File Path                                        | Responsibility                                        | Important Functions                                           | Dependencies                       | Connected Files                  | Request/Data Flow                                                          | Security Considerations                                          | Performance Considerations                              |
| ------------------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------- | ---------------------------------- | -------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------- |
| `apps/admin/src/App.tsx`                         | Responsive admin shell and management views.          | Login, dashboard, product/category/customer/inventory/order views, `ProductDialog` | React, MUI, admin API client       | `api.ts`, API admin routes       | User action -> API client -> database response -> table/form state; product forms load category options from the backend | Role is checked during login and API checks it again server-side; failed saves retain form data | Views load only their active data section; mobile navigation uses a temporary drawer and dense tables scroll horizontally |
| `apps/admin/src/api.ts`                          | Admin HTTP client and typed responses.                | Access-token interceptor, refresh single-flight, CRUD methods | Axios                              | `App.tsx`, auth/admin API        | In-memory access token -> request header; refresh cookie restores sessions | No refresh token or password is stored in browser state          | Single-flight refresh avoids duplicate refresh requests |
| `apps/web/src/App.tsx`                            | Customer catalogue, cart and wishlist UI.             | `ProductImage`, product/cart/wishlist actions               | React, MUI, customer API client    | Catalogue API and cart/wishlist routes | Product response -> consistent image or placeholder -> customer action | Protected customer actions use the existing authenticated API client | Placeholder rendering avoids broken image layout when imageUrl is null |
| `apps/admin/src/styles/global.scss`               | Admin responsive browser baseline.                    | Global box sizing, overflow and typography rules              | SCSS                              | `main.tsx`, `App.tsx`               | Browser viewport -> predictable sizing and overflow behavior          | No application data handled                                             | Prevents viewport-wide horizontal overflow on small screens |
| `apps/web/src/styles/global.scss`                 | Customer responsive browser baseline.                 | Global box sizing, overflow and image rules                    | SCSS                              | `main.tsx`, `App.tsx`               | Browser viewport -> predictable sizing and overflow behavior          | No application data handled                                             | Keeps images within their containers and prevents page overflow |
| `apps/api/src/modules/admin/admin.routes.ts`     | Protected admin route registration.                   | Route declarations                                            | Express, auth middleware, Zod      | `app.ts`, controller, validation | Request -> authentication -> ADMIN role -> controller                      | Every route requires ADMIN authorization                         | Shared middleware centralizes checks                    |
| `apps/api/src/modules/admin/admin.controller.ts` | HTTP response mapping and business error translation. | Dashboard, CRUD, inventory handlers                           | Express, Prisma errors, repository | Routes and repository            | Validated request -> scoped repository query -> safe JSON                  | Never selects password hashes or refresh tokens                  | Pagination is passed to repository queries              |
| `apps/api/src/modules/admin/admin.repository.ts` | Database queries and selective projections.           | Stats, product/category/customer/inventory queries            | Prisma                             | Controllers, existing models     | Controller -> transaction/query -> selected fields                         | Customer and product responses exclude credentials               | Counts and pagination execute in database               |
| `apps/api/src/modules/admin/admin.validation.ts` | Zod request validation.                               | List, CRUD, inventory schemas, optional image URL normalization | Zod                                | Routes, validation middleware    | Request body/query/params validated before persistence                     | Bounds prices, stock, IDs, slugs and rejects invalid non-empty image URLs | Rejects invalid requests before Prisma                  |
| `apps/api/tests/admin-validation.test.ts`       | Regression tests for admin product request validation. | Optional/valid/invalid image URLs and quantity rules          | Jest, Zod                          | Admin validation schema           | Representative payloads -> parsed or rejected request data                 | Ensures invalid values cannot reach product persistence                 | Fast schema-level coverage                            |
| `apps/admin/src/App.tsx`                         | Admin order listing and status management.             | `Orders`, search/filter, status transition actions             | React, MUI, admin API client       | `apps/admin/src/api.ts`, order routes | Admin action -> protected API -> order table/detail state                 | Server enforces ADMIN role and status transitions                         | Paginated API query supports bounded result sets       |
| `apps/admin/src/api.ts`                          | Typed admin order API methods.                         | `orders`, `order`, `updateOrderStatus`                         | Axios                              | `App.tsx`, admin order routes       | In-memory access token -> admin order request                              | Refresh token remains HTTP-only                                            | Query parameters support server-side filtering         |
| `apps/web/src/api.ts`                             | Typed customer order API methods and models.           | `orderApi.create/list/get/cancel`                              | Axios                              | `App.tsx`, customer order routes    | Checkout address -> API -> order response                                  | Customer ownership is enforced by backend                                 | Uses existing in-memory token and refresh flow         |
| `apps/web/src/App.tsx`                            | Customer checkout and payment result UI.              | Payment selection, provider result, retry and status display    | React, MUI, customer API client    | `api.ts`, payment/order routes     | Checkout -> server payment orchestration -> success/failure/cancel state       | Client cannot set final payment status                                      | Retry reuses the unique payment record                  |
| `apps/api/src/modules/payments/payment.provider.ts` | Provider contract for payment operations.             | `PaymentProvider`                                              | TypeScript                         | Factory, service, provider implementations | Service -> provider -> verified result                                    | Keeps gateway implementation behind a server boundary                      | Enables provider replacement without checkout changes    |
| `apps/api/src/modules/payments/mock-payment.provider.ts` | Deterministic mock provider.                         | `createPayment`, `verifyPayment`                                | Node crypto, provider contract     | Payment factory and service       | Payment method -> simulated provider outcome                                  | Final status is provider-controlled                                         | No external network dependency                           |

| `apps/api/src/modules/notifications/notification.service.ts` | Persists, deduplicates, projects, and emits notifications. | `publish`, `notifyAdmins` | Prisma, Socket.IO gateway | Order/payment services | Successful business operation -> notification persistence -> real-time event |
| `apps/api/src/modules/notifications/notification.gateway.ts` | Authenticated Socket.IO gateway and recipient rooms. | Token middleware, `notification:new` | Socket.IO, JWT verification | HTTP server, notification service | Handshake token -> verified subject -> server-controlled room | Clients cannot choose rooms |
| `apps/api/src/modules/notifications/notification.controller.ts` | Notification list and read-state HTTP handlers. | List, unread count, mark read/all | Express, notification service | Notification routes | Authenticated request -> recipient-scoped query | Ownership is applied from JWT |
| `apps/web/src/api.ts` | Customer notification API and model types. | `notificationApi` | Axios | Customer app | In-memory access token -> notification API | Refresh token remains HTTP-only |
| `apps/admin/src/App.tsx` | Admin notification list, unread count, and real-time updates. | `Notifications` | React, MUI, Socket.IO client | Admin notification API | Socket/API events -> notification state | Only the authenticated admin's room is used |       | Payment method -> simulated provider outcome                                  | Final status is provider-controlled                                         | No external network dependency                           |
| `apps/api/src/modules/payments/payment.factory.ts` | Selects configured payment provider.                 | `paymentProvider`                                               | Environment config                 | Payment service                   | Environment -> provider instance                                             | Provider selection stays server-side                                        | Single provider instance                                |
| `apps/api/src/modules/payments/payment.service.ts` | Payment business rules and orchestration.             | `create`, `get`, `getForOrder`                                  | Prisma, provider, repository       | Payment controllers and order model | Owned order -> server total -> provider -> transactional status update        | Validates ownership and rejects client totals/status                         | Reuses the unique order payment on retries              |
| `apps/api/src/modules/payments/payment.repository.ts` | Payment persistence and status updates.              | `createPending`, `updateResult`, ownership queries              | Prisma                             | Payment service and schema         | Service -> payment/order transaction                                         | Scopes reads through order ownership                                        | Unique order constraint prevents duplicate records       |
| `docs/phase-5-order-management.md`               | Phase 5 architecture and lifecycle documentation.     | Order flow, status lifecycle, file inventory                    | Markdown                           | Prisma, API and frontend modules    | Documents transaction and authorization boundaries                         | Explicitly records customer/admin separation                               | Captures snapshot and transaction decisions            |
| `docs/api-documentation.md`                       | API contract and product payload documentation.       | Admin product request rules                                   | Markdown                           | Admin API and admin form         | Documents category selection and optional image behavior                    | Documents server-side category validation                         | Keeps clients aligned with request validation           |
| `apps/api/src/app.ts`                            | Mounts the admin API module.                          | `/api/v1/admin` registration                                  | Express                            | Admin routes                     | Express request enters protected module                                    | No frontend-only authorization reliance                          | One shared route boundary                               |

Orders, payments, and notifications are pending until corresponding database
models and workflows are introduced.
