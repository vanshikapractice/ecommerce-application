## Data flow

1. A customer signs in or restores a session. The access token is held in memory and the refresh token remains an HTTP-only cookie.
2. The customer API client sends the access token to `/api/v1/cart` and `/api/v1/wishlist`.
3. Authentication middleware validates the token and exposes only `request.auth.sub`.
4. Repository queries filter by that user ID. Composite keys prevent duplicate item rows.
5. Cart totals are calculated from Prisma `Decimal` prices and current quantities.
6. Frontend mutations replace local state with the server response, so stale client totals cannot be trusted.

## API summary

- `GET /api/v1/cart`
- `POST /api/v1/cart/items` with `{ productId, quantity }`
- `PATCH /api/v1/cart/items` with `{ productId, quantity }`
- `DELETE /api/v1/cart/items/:productId`
- `DELETE /api/v1/cart`
- `GET /api/v1/wishlist`
- `POST /api/v1/wishlist/items` with `{ productId }`
- `DELETE /api/v1/wishlist/items/:productId`

All endpoints require a valid access token. Product prices and stock are never accepted from the browser.
